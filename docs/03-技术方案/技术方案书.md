## 三、已实现技术方案

### 3.1 认证与授权架构

**JWT 认证流程：**

```
POST /api/v1/auth/login
  → 验证 username/password
  → 生成 access_token (30min) + refresh_token (7day)
  → 前端存入 localStorage
  → 后续请求携带 Authorization: Bearer <token>
```

**RBAC 角色体系：**

| 后端 role_type | 前端角色标识 | 数据库 role_code | 核心职责 |
|---|---|---|---|
| `setup` | `company_admin` | `admin` | 系统初始化、用户管理、科目映射 |
| `finance` | `finance_manager` | `finance_manager` | 审批、税务管理、查看所有报表 |
| `accounting` | `accountant` | `accountant` | 凭证录入、发票、工资、资产等核心记账 |
| `cash` | `cashier` | `cashier` | 资金收付、银行流水、发票开具/领购 |
| `query` | `company_manager` | `company_manager` | 查看报表、凭证总览，无录入权限 |

**跨角色权限规则（`security.py` 内置）：**
- `finance` 可跨读 `cash` 和 `accounting` 资源
- `is_system_admin` / `is_superuser`  bypass ALL 角色检查

### 3.2 发票导入两遍处理流程

**技术架构：**

```
Excel 上传
  │
  ▼
┌─────────────────────────────────────┐
│ 第一遍：数据收集与解析               │
│ · 列名映射 (COLUMN_ALIASES)         │
│ · 行数据解析                         │
│ · 状态分类 (classify_invoice)       │
│ · 备注提取原发票号 (正则匹配)        │
│ · 结果: all_rows 集合                │
└─────────────────┬───────────────────┘
                  │
  ▼
┌─────────────────────────────────────┐
│ 第二遍：按优先级排序处理             │
│ · 设定优先级:                        │
│   normal=0 → redflush=1 →           │
│   voided=2 → redchar=3             │
│ · 按优先级排序 all_rows              │
│ · 单次循环处理所有发票:              │
│   1. normal → 创建 issued 记录      │
│      自动生成凭证                    │
│   2. redflush → 查找同批或历史正常   │
│      发票，标记为 voided             │
│      创建红冲记录                    │
│   3. voided → 创建作废记录          │
│   4. redchar → 创建红字记录         │
└─────────────────────────────────────┘
```

**红冲识别规则（优先级）：**

| 优先级 | 判断条件 | 分类结果 |
|---|---|---|
| 1 | `total_amount < 0` 或 `amount < 0` | 红冲发票 |
| 2 | 状态列包含 "红冲" | 红冲发票 |
| 3 | 状态列包含 "作废" | 作废发票 |
| 4 | 以上都不是 | 正常发票 |

**备注提取正则：**
```python
r'被红冲蓝字(?:数电)?发票号码[：:]\s*(\d+)'
```

### 3.3 共享计税服务层

**文件：** `backend/app/services/tax_calculation.py`

**核心函数：**

| 函数名 | 功能 |
|---|---|
| `get_period_revenue_and_expense(db, period_id)` | 获取期间收入费用（科目余额） |

## 四、关键技术决策总结

| 决策点          | 方案                        | 理由                  |
| :----------- | :------------------------ | :------------------ |
| **后端框架**    | FastAPI (Python)          | 高性能异步、开发效率高、与 Python 生态无缝集成 |
| **前端框架**    | Vue 3 + Composition API    | 轻量、响应式、Element Plus 生态丰富 |
| **ORM**       | SQLAlchemy 2.0            | 类型安全、支持异步、Python 最成熟 ORM |
| **认证**       | JWT (HS256)               | 无状态、适合 REST API     |
| **权限**       | RBAC (role_type + require_roles) | 灵活可扩展、代码内置跨角色规则 |
| **发票导入**    | 两遍处理引擎                   | 确保红冲发票正确关联原发票并标记作废 |
| **税金计算**    | 共享服务层 (tax_calculation.py) | 消除重复代码、保证计算一致性    |
| **凭证生成**    | 审核时自动生成                   | 减少人工操作、保证财务数据完整性   |

## 五、技术风险与缓解

| 风险                 | 缓解措施                          |
| :----------------- | :---------------------------- |
| 发票 Excel 格式不兼容    | 统一列名映射系统 (COLUMN_ALIASES)，支持多种变体 |
| 红冲发票无法匹配原发票      | 四级匹配策略（发票号 → 税号+金额 → 名称+金额 → 备用） |
| 计税逻辑重复            | 共享服务层抽取，消除重复代码            |
| 权限配置错误            | 路由级 + API 级双重校验，定期审计       |
| 数据一致性            | 数据库事务 + ORM 约束             |
| 性能瓶颈              | 索引优化、查询分析、必要时引入 Redis 缓存  |
