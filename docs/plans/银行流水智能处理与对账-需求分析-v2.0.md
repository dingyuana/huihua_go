## 1. 核心设计原则（融合定稿）

| # | 原则 | 说明 |
|---|------|------|
| **P1** | **人本原则** | 人是最终审核者与决策者。任何系统自动操作均不可越过人工确认环节。 |
| **P2** | **AI辅助原则** | AI 发挥最大能力，主动完成信息识别、分类建议、草稿生成。将人工从重复性录入中解放。 |
| **P3** | **草稿非正式原则** | 所有由系统自动生成的下游单据（凭证、收款单、付款单），初始状态均为**草稿**。草稿不计入科目余额，不参与账务核算，不完成对账。 |
| **P4** | **原子性原则** | 人工【提交审核】操作，在一个数据库事务中原子性完成：流水状态变更 → 草稿转正 → 银企勾对。 |
| **P5** | **规则+AI双轨制** | 以规则引擎为稳定底座，AI 分析为智能增强。规则保证确定性业务（银行/税务/社保/保险/利息），AI 处理模糊场景（收款/付款/货款）。规则优先，AI 兜底。 |

### 2.2 状态机（BankTransaction.status）

```
[pending] ──AI分析──▶ [classified] ──确认──▶ [approved] ──分流──▶ [voucher_generated / payment_created / manual_pending]
                              │
                              └──▶ [manual_pending]（驳回）
```

| 状态值 | 含义 | 说明 |
|--------|------|------|
| `pending` | 待审核 | 导入后初始状态；或 AI 无法处理的人工待办状态 |
| `classified` | 已分类 | AI 已分析并给出分类建议，有/无草稿 |
| `approved` | 已审核 | 人工提交确认，代表该笔流水已被正确处理 |
| `voucher_generated` | 已生成凭证 | A类流水（银行/税务/社保/利息/保险）已自动制证 |
| `payment_created` | 已生成收付款单 | B类流水已生成收款单/付款单 |
| `manual_pending` | 待人工处理 | C类或其他被驳回的流水，需人工介入 |

### 2.3 下游草稿单据（Draft Documents）

| 草稿类型 | 正式类型 | 状态字段 | 说明 |
|-----------|----------|----------|------|
| VoucherDraft | JournalEntry | docstatus=0 | 凭证草稿，不入账 |
| ReceiptDraft | PaymentEntry (receipt) | status=draft | 收款单草稿 |
| PaymentDraft | PaymentEntry (payment) | status=draft | 付款单草稿 |

**草稿转正条件（业务校验）**：
- 借方科目 ≠ 贷方科目
- 科目非停用状态（is_active=true）
- 金额合计为零（借贷平衡）
- 附件数量在允许范围内

### 2.4 业务单据（BusinessDocument）— 扩展已有 PaymentEntry

已在 `internal/model/payment.go` 定义 `PaymentEntry`，扩展支持：

| 字段 | 说明 |
|------|------|
| doc_type | receipt / payment（覆盖） |
| source_bank_txn_id | 来源银行流水 |
| voucher_id | 关联凭证（生成后填充） |
| status | draft / confirmed / voided |
| auto_generated | bool，是否 AI 自动生成 |

## 3. 四阶段业务流程详解

### 3.1 第一阶段：导入与 AI 智能分析

```
[用户导入 Excel]
      ↓
[后台解析] → bank_transactions 表（status=pending）
      ↓
[AI 分析服务]（或规则引擎兜底）
  传入: description / counterparty / amount / direction
  返回: business_scene / suggested_action / confidence / template_suggestion
      ↓
┌─────────────────────────────────────────┐
│ 高置信度(≥80) + suggested_action ≠ manual │
│   → 后台静默创建草稿（凭证草稿/收款单草稿/付款单草稿） │
│ 低置信度(<60) or suggested_action=manual │
│   → 无草稿，标记 manual_pending，不创建草稿 │
└─────────────────────────────────────────┘
      ↓
[前端展示：银行流水审核工作台]
  - AI已处理列表（有草稿）
  - 待处理列表（无草稿 / manual_pending）
```

**AI 分析接口**（内部调用，非用户触发）：
- 请求：`POST /internal/ai/analyze`
- 请求体：多笔流水的 description / counterparty / amount / direction
- 响应：每笔的 business_scene / suggested_action / confidence / template_suggestion

**规则引擎兜底**（当 AI 服务不可用时）：
- 按已有 `ClassificationRuleService` 规则匹配
- 命中则 confidence=75（规则默认）
- 未命中则 classification=pending, confidence=0

### 3.2 第二阶段：人工审核与修正决策

```
[银行流水审核工作台]
      ↓
[查看] 流水原始信息 + AI分析结果 + 置信度 + 命中规则名
      ↓
[预览草稿] 点击流水 → 弹窗查看凭证/收付款单草稿详情
      ↓
[修正决策]
  A. 直接修改草稿（科目/金额/摘要）
  B. 变更处理方式（强制变更：auto_voucher → auto_receipt_payment）
  C. 驳回至待处理（取消草稿关联，标记 manual_pending）
      ↓
[提交审核] 单笔/批量勾选 → 点击「提交审核」
```

**操作按钮**：
- 「提交审核」：仅对 classified 状态且有草稿的流水
- 「驳回至待处理」：取消草稿，进 manual_pending
- 「直接生成」：无草稿时，可手动选择类型生成正式单据

### 3.3 第三阶段：原子性提交与闭环

**触发**：人工点击「提交审核」

```
[事务开始]
  │
  ├── 1. 状态变更: pending/classified → approved
  │
  ├── 2. 草稿转正（分类讨论见 4. 分流规则）
  │     - 凭证草稿 → JournalEntry（docstatus=1）
  │     - 收款单草稿 → PaymentEntry（status=confirmed）
  │     - 付款单草稿 → PaymentEntry（status=confirmed）
  │     - 业务校验失败 → 事务回滚 + 返回错误提示
  │
  └── 3. 银企勾对（自动）
        - 该银行流水.matched = true
        - 该银行流水.matched_journal_entry_id / matched_document_id 填充
        - 凭证/收付款单标记为已勾对
[事务提交]
```

**场景二（已有匹配单据）**：
- AI 分析时若匹配到现存未勾对的收款单/付款单，人工确认后直接勾对，不重新生成单据

### 3.4 第四阶段：待人工处理

```
[待处理工作台]
  - 展示所有 manual_pending 流水
  - 每笔显示：原始流水信息 + 建议（AI 或规则引擎）
      ↓
[人工选择处理方式]
  - 做凭证（手动录入全部分录）
  - 做收款单 / 做付款单（手动录入）
  - 做其他单据
      ↓
[点击「手动完成并确认」]
  - 流水状态 → approved
  - 单据直接记为正式（无草稿阶段）
  - 自动勾对完成（matched=true）
```

## 4. 分流规则（核心）

### 4.1 三类分流

| 类别 | 判断条件 | 自动动作 | 生成结果 |
|------|----------|----------|----------|
| **A类：银行/税务/社保/利息/保险** | classification ∈ {bank_fee, tax_payment, social_security, insurance_fee, interest_income} | 提交审核时**自动生成凭证** | JournalEntry (docstatus=1) |
| **B类：收款/付款/货款** | classification ∈ {business_receipt, business_payment} | 提交审核时**生成收款单/付款单** | PaymentEntry (doc_type=receipt/payment, status=confirmed) |
| **C类：其他不明确** | classification = pending OR AI suggested_action=manual | 进入**待处理工作台**，人工处理 | 无自动生成 |

### 4.2 A类详细映射

| classification | 借方科目 | 贷方科目 | 摘要模板 |
|----------------|----------|----------|----------|
| bank_fee | 5602 财务费用 | 银行活期存款（清算账户） | 银行手续费 |
| interest_income | 银行活期存款 | 5602 利息收入 / 6011 投资收益 | 存款利息 |
| tax_payment | 应交税费(2221) | 银行活期存款 | 税款支付 |
| social_security | 应付职工薪酬(2211) | 银行活期存款 | 社保缴纳 |
| insurance_fee | 管理费用(5601) | 银行活期存款 | 保险费 |

> **前置条件**：科目代码 5601/5602/2221/2211/1002 必须存在，否则生成失败并回滚事务

### 4.3 B类详细映射

| classification | 单据类型 | 款项性质 | 往来单位 |
|----------------|----------|----------|----------|
| business_receipt | 收款单 | 货款/预收款/回款 | counterparty_name 填充 |
| business_payment | 付款单 | 货款/采购款/费用款 | counterparty_name 填充 |

### 4.4 置信度评估

| 置信度 | 来源 | 建议操作 |
|--------|------|----------|
| ≥80 | 精确匹配客户/供应商 OR 高置信度 AI | 一键确认 |
| 60-79 | 模糊匹配 OR 规则命中 | 重点核对 |
| <60 | 关键词匹配 OR 低置信度 AI | 建议人工判断 |
| 0 | 兜底未命中 | 强制人工处理 |

## 8. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| AI 服务不可用 | 流水无法自动分析 | 规则引擎兜底，保证核心流程可用 |
| 科目缺失导致 A 类制证失败 | 事务回滚，用户体验差 | 提交前预检查科目是否存在，缺失则提前提示 |
| 存量数据状态迁移 | 历史数据不一致 | migration 脚本 + 上线前备份 |
| 草稿堆积无人处理 | 陈旧草稿污染工作台 | 草稿清理策略：>30天未处理提示出纳 |
| B 类收款单/付款单生成后发票核销复杂 | Phase 2 延期风险 | Phase 1 先做收款单/付款单生成，核销后续扩展 |

## 10. 验收标准

| # | 标准 | 验证方式 |
|---|------|----------|
| V1 | 流水导入后 status=pending，AI 分析后更新 confidence + suggested_action | API 测试 |
| V2 | 高置信度(≥80)流水自动生成草稿（凭证草稿/收款单草稿/付款单草稿） | 数据库查询 draft_voucher_id / draft_payment_id |
| V3 | 低置信度(<60)流水无草稿，status=manual_pending | 数据库查询 |
| V4 | 「提交审核」在事务中原子完成：状态变更+草稿转正+勾对 | 事务测试（模拟失败验证回滚） |
